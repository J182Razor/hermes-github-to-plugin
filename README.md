# github-to-hermes: current status

**Partial, experimental implementation.** Conversion does not execute repository source; invoking generated adapters does, with the user's OS privileges and no security sandbox. Review all generated code and source manually before enabling or sharing. A successful conversion or test does not guarantee safety, compatibility, or correctness. Unknown types and detection score ties fail closed.

## Conversion and prerequisites

Provide a credential-free `https://github.com/owner/repo` URL. Git must be installed and the repository accessible without inherited Git credentials or prompts; private-repository authentication is not supported. The converter requires Python 3.11+, PyYAML for YAML metadata and OpenAPI, and on Windows pywin32 for private clone-directory ACLs. Install prerequisites separately: conversion never installs packages. Generated adapters have additional separately provisioned runtime requirements described below.

Without `output_dir`, output is staged under the Python temporary directory in `g2h_output`; each plugin occupies its own child directory. The default child name is `g2h-`, a normalized lowercase owner/repository slug (truncated as necessary), and a 16-hex SHA-256 suffix of the lowercase canonical `owner/repo` (with `.git` removed). The component is at most 64 characters, as are explicit names. URL casing and a `.git` suffix do not distinguish repositories. Existing paths are never overwritten: a repeated conversion must use a different explicit `name` or an empty output location. A generated scaffold is staged for review, not installed, enabled, or automatically validated; runtime compatibility is verified only for the limited synthetic cases below.

Automatic console MCP conversion requires static evidence of a direct unaliased FastMCP import, one uniquely bound instance, and its direct `run()` call as the sole executable statement in the console entry function; a direct unaliased one-hop function re-export is supported. Metadata, README text, a dependency, and an unused import are not evidence. Other patterns require source review and explicit `type=mcp`, and remain subject to the supported subset. Static syntax is evidence, not proof of runtime behavior or safety: imports and source can be dynamically modified. Conversion never grants runtime consent; existing approval and opt-in gates still apply.

## Validation

`validate_plugin` performs bounded, non-executing checks of selected native or portable plugin metadata. `success: true` means only those supported static checks passed; `static_only` is true and `runtime_validation` is `not run`. It does not check source, dependencies, registration, skills, or full loader semantics, and is neither full Hermes validation nor a security assessment. Concurrent filesystem changes are not prevented. Native metadata checks require separately provisioned PyYAML; no dependencies are installed by this tool.

Optional `mode: "runtime"` copies a bounded snapshot (2,000 entries, 16 MiB), computes a SHA-256 manifest of paths and contents, and directly invokes the standard Hermes approval gate with that digest and a unique rule key. **This executes plugin registration code with the same OS privileges as Hermes, potentially more than once. There is no sandbox, network isolation, or process-tree termination guarantee.** Review the source before requesting it. YOLO, approvals off, cached approvals, or unattended policy may bypass a prompt; a gate result is not proof of fresh human consent. Denial or an unavailable gate prevents launch. The snapshot rejects symlinks, reparse points and hardlinked files, but copying and rechecking are not atomic against the same user; dynamic imports can read outside the snapshot. Windows alternate data streams are not copied or audited. Snapshot content may contain secrets; it is staged in a private temporary directory (Windows requires pywin32 ACL support) and removed best effort.

After the gate, a disposable Python child calls the host `validate_plugin_dir` and, for native manifests, `doctor_plugin` APIs directly; it does not use the Hermes launcher or install dependencies. Portable doctor is reported unsupported. These APIs can execute source and spawn their own processes. The child has a minimal environment and a 60-second deadline, but termination of descendants is not guaranteed. Child stdout/stderr are discarded and host failures are sanitized; this does not stop approved code from accessing files or sending data elsewhere. The controlled status report and diagnostic reasons are not tamper-proof against code running with the same account, nor against other same-user adversaries. Native success requires both host checks to pass; portable success requires validation to pass and doctor to be unsupported. Cleanup failures make the operation unsuccessful while retaining any completed check results and a sanitized warning. Results are not a security assessment.

## Supported scope and limits

- Single-file entrypoints use one synchronous top-level `module:function`. Undecorated callables require no arguments and literal defaults. A narrow Click CLI subset also supports unaliased `import click`, `@click.command()` or `@click.group()`, `@click.option()`/`@click.argument()`, and statically declared group subcommands. Click must be a declared, preinstalled dependency. Its generated tool accepts `argv`: at most 64 strings, each at most 4096 characters, at most 16384 UTF-8 bytes in total, no NUL; arguments are never passed through a shell. Other decorated or ambiguous forms are unsupported. CLI adapters reject direct `__file__` references because copied source changes file-resource semantics; indirect resource assumptions cannot be detected reliably. In particular the Click aliases example uses `__file__` for reads and writes and is unsupported. CLI adapters accept a restricted subset of declared dependencies with numeric release comparisons, check installed distribution metadata after approval and before source execution, and never install dependencies. This check does not establish package integrity or importability; unsupported versions fail closed. Non-CLI single-file entrypoints reject declared dependencies; optional dependencies and dynamic project metadata are unsupported. Undeclared imports must already be available. Static checks do not prove behavior or prevent runtime failures.
- Dotted package entrypoints use a different adapter: CLI functions take no Python parameters and expose an `argv` string array; Python function parameters require `str`, `int`, `float`, or `bool` annotations and compatible literal defaults. Variadic, decorated, async, and ambiguous signatures are unsupported. Dependencies are not installed automatically. Resources are limited to exact flat filenames under `[tool.setuptools.package-data]` for regular packages (no globs, nested paths, or wildcard package names): `.txt`, `.json`, `.csv`, `.yaml`, `.yml`, `.toml`, `.xml`, `.html`, `.md`, `.dat`; at most 128 files, 256 KiB each and 1 MiB total. Undeclared files, non-package directories, symlinks/reparse points, sensitive-looking filenames and private-key header canaries are rejected. These checks cannot prove secrets are absent; review all copied source and resources. Each file is hashed and checked before source invocation; `importlib.resources.files(__package__).joinpath('name').read_text()` and `read_bytes()` read verified in-memory bytes. Filesystem paths and `__file__`-based resource access are unsupported; literal `__file__` use is rejected when resources are declared. Static checks cannot detect every dynamic access. Hash verification and local file reads do not defend against hostile concurrent local mutation or edits to the adapter, and approved source has full OS privileges.
- MCP conversion supports a top-level Python stdio server script (at most 12,000 source bytes) or a bounded regular multi-file Python package invoked with `-m`; environment overrides and unsupported resources are rejected. Package collection caps its base64 envelope at 65,536 ASCII bytes; the separately bounded bootstrap stdin frame is at most 1 MiB. This is separate from the Windows CreateProcessW limit of 32,767 UTF-16 code units including the terminating NUL. Before spawning, the worker measures the complete Windows-quoted command line, including interpreter path, flags and static bootstrap, and rejects it if over that limit. Local symbol imports must be statically recognizable as top-level declarations or package submodules; ambiguous dynamic and star imports are rejected. Static checking does not guarantee imports or execution will succeed. Invocation works only on Windows with assignable job containment and requires an operator-created `persistent-mcp-opt-in.txt` in the plugin data directory containing exactly `I TRUST THIS SOURCE WITH PERSISTENT FULL OS AUTHORITY` in UTF-8, with no newline. The source and MCP session persist between calls; source and descendants run with the user's full OS privileges and can continue between calls and after a later denial or removal of the opt-in file. There is no idle timeout. Per-call host approval is subject to host policy and overrides; neither approval nor job containment is a sandbox. Trust the source, adapter and host boundary before enabling. The opt-in file is not a security boundary against an agent or process able to modify it or the adapter files. Static checks cannot discover every dependency.
- Generated portable MCP servers require `python` on the Hermes process PATH with the MCP SDK and any reviewed source dependencies already installed; none are installed automatically. Fixed CLI/Python adapters require MCP SDK 2.x. Deferred MCP's tested SDK versions include 1.9.4, 2.0.0 and 2.3.0; other versions are not generally guaranteed. Windows execution requires assignable job objects and `NtResumeProcess`; deferred MCP fails closed on other platforms. Other platform/runtime combinations are not generally guaranteed.
- Console project metadata exposes only the reviewed, static name and exact numeric version in memory, with standard normalized-name lookup; distribution resources, entry points and other metadata are unsupported. A same-name installed distribution or dependency is rejected rather than shadowed.
- When `mcp.json` is absent, automatic conversion selects the limited `pyproject.toml` console format only when the detector selects MCP and the generator validates the structural metadata and package; explicit type `mcp` remains available for reviewed sources. Detection and metadata do not establish trust or safety. MCP dependencies with automatic CLI detection fail as ambiguous; explicitly select `cli` or `mcp` after inspection. It requires one `[project.scripts]` entry of the form `package:function`, a regular `src/package` tree, and exactly one `mcp` dependency; optional/dynamic dependencies and anything other than simple numeric release comparisons are rejected. Metadata is bounded to 1 MiB, the package to 64 entries and a 65,536-byte encoded envelope. Only regular Python package files are supported, and the function must be a statically identifiable undecorated synchronous no-required-arguments definition in `__init__.py`. No source is imported during conversion. All declared distributions must already satisfy their constraints in the worker interpreter; metadata checks do not establish importability or package integrity. Review the generated manifest, code and source, and create the documented persistent-authority opt-in only after trusting them; approved code has full OS authority.

Known gaps:
- OpenAPI methods are limited to GET, POST, PUT, PATCH, and DELETE. Where request bodies are supported, they are JSON objects with restricted declared property schemas; multipart and schema-valued `additionalProperties` are unsupported. Extra JSON properties are permitted by default or when explicitly allowed, subject to a 64-level nesting limit and a 65,536-byte serialized-body limit. Serialization occurs before that size check, so the limit is not a pre-allocation bound.
- OpenAPI root `tags` and `externalDocs` are descriptive metadata and are not retained. One literal HTTPS root server is supported; only its static path affects requests, while its declared origin does not authorize or select the destination. Server paths ending in `/` are rejected because joining them to operation paths would create double slashes; they are not silently normalized. Configure `base_url` separately. Operation allowlists must use the effective root-prefixed path template: with root `/api/v3`, explicitly approve `GET /api/v3/echo`, not `GET /echo`. Existing policies are never silently upgraded; review and update them when regenerating. No-server policies remain unchanged. Multiple servers, variables, and server overrides are unsupported.
- All supported OpenAPI adapters, including unauthenticated GET-only specs, use an operator-controlled plugin-data `openapi-authorization.json`, containing `base_url` (exact origin) and `operations` (exact `METHOD /path-template` strings). GET can mutate state. Calls are marked untrusted and request host per-call approval, subject to host policy overrides; approval is not an OS sandbox. Protect configuration and adapter files from model writes; they are not hardened against the same OS user. Private hosts may be explicitly authorized; DNS remains trusted, and proxies and redirects are disabled.
- OpenAPI path argument values are restricted to ASCII unreserved characters (`A-Z`, `a-z`, `0-9`, `-._~`); Unicode, percent escapes, slashes, and other characters are rejected. Complete substituted paths are also checked for dot segments and encoded separators. This intentionally excludes some otherwise valid API identifiers, and cannot guarantee how a remote service or intermediary interprets paths. Query, body, and header values retain their existing validation and transport limitations. Regenerate existing adapters to apply changes.
- Migration: previously generated native GET plugins remain unchanged and unsafe until disabled and replaced. Regenerate them as portable MCP plugins, configure `openapi-authorization.json` in the plugin data directory, and review the host trust policy. The old `G2H_ALLOWED_BASE_URL`, `G2H_APPROVED_GET_PATHS`, and `base_url` tool argument do not configure the new adapters.
- Portable OpenAPI authentication supports one HTTP bearer or header API-key scheme with global and per-operation security. Set `G2H_API_CREDENTIAL` in the host environment before starting the server; generated config contains a placeholder, not the secret. Query/cookie keys, OAuth, alternative/combined requirements and multiple schemes are rejected. Authenticated calls require HTTPS except HTTP to an explicit literal IPv4 127.0.0.0/8 or IPv6 ::1 loopback address for controlled local testing. DNS names such as localhost, mapped IPv4 and userinfo are not loopback exceptions. Direct and JSON-decoded credential echoes fail closed, and direct credentials in arguments are rejected, but encoded, split, partial, transformed or unrelated secrets cannot reliably be detected; never put secrets in arguments or responses.
- CLI/Python adapters copy source scripts without scanning content. Scripts may embed arbitrary secrets; review them before sharing and before enabling.
- Skill bundles reject known sensitive filenames, special files, symlinks and Windows reparse points before output creation. This filename denylist is incomplete: arbitrary files can contain secrets, so review all content before sharing or enabling. Traversal and copying are not atomic and are unsafe against concurrent source mutation.
- Generated fixed CLI/Python adapters use portable MCP and have been exercised through the local Hermes portable loader and MCP SDK stdio initialize/list/call with synthetic source. The `python` on PATH must already have Python MCP SDK 2.x and source imports installed. Hermes `untrusted` requests its write-capable per-call gate under the user's policy; user configuration or bypass modes can override it. Digest verification rejects modified source before starting its child, but adapter files themselves must be trusted.
- Fixed adapters have a 30-second limit, 1 MiB stdout and 4 KiB stderr caps. Both streams are returned even on success and are not redacted; source output can contain sensitive data. Deferred MCP requests use a 30-second deadline and a 1 MiB serialized worker-response limit, checked after the MCP SDK has parsed the source response; it is not a streaming or pre-parse memory bound. Windows jobs cap committed memory at 256 MiB per process and 512 MiB aggregate, but not the host process, and are not a sandbox. Process termination/reaping can exceed the request deadline. Process-tree cleanup is best effort: POSIX children can escape via a new session; detached services and hostile local users are outside its guarantees. REST requests run with at most four workers per server; further calls fail immediately rather than queue. Workers have a 10-second total deadline and a 1 MiB response cap; cancellation terminates and reaps the worker before releasing its slot. This is not a security sandbox.
- Typed Python and package CLI workers request memory limits and therefore fail closed before spawning on non-Windows systems; no POSIX memory cap is implemented. Their separately returned stdout and stderr are UTF-8 decoded with replacement and are unredacted, so source logs may contain sensitive data. Regenerate adapters to apply these changes.
- Generated tool and toolset names have a plugin-specific hash and reserved-looking prefix; actual registration against all Hermes versions and all installed tool names has not been verified.
- Output path components are checked for symlinks and Windows reparse points before conversion; generator directories are created exclusively. These checks are not atomic: malicious same-user mutation can redirect writes or replace paths after checking. Direct generator calls bypass the converter's component checks. Failed generation can leave partial output for manual inspection.
- Clone parent components are checked for links, and cleanup checks the original directory identity. These checks and recursive deletion remain race-prone, including against replacement after verification. POSIX temporary directories are checked for owner-only mode; Windows clone directories use a protected owner-only ACL that is verified and fail closed when required Windows ACL support or verification is unavailable. Source traversal checks are not atomic against junction substitution.
- Detection is heuristic and may select the wrong type; ties and unsupported sources fail closed.
- Cloning accepts only credential-free GitHub HTTPS owner/repository URLs and disables inherited Git config, credentials, prompts, redirects and hooks. Clone directories are cleaned after detection/conversion, but deletion is not race-free against directory substitution; use a private scratch directory. Git itself is trusted and cloning is not a sandbox.
- Default validation performs limited static checks only. Optional runtime validation executes source as described above; neither mode is a security audit.

Do not supply secrets in URLs or reports. Never run unreviewed code, enable a generated plugin, or expose it to an agent until the implementation has been hardened and tested end to end.

Offline regression tests (Bash; use native paths on Windows):

```sh
# Set these to your local checkout, its prepared Python interpreter, and a
# private writable scratch directory. Do not commit the resulting values.
export HERMES_SOURCE_ROOT="<absolute-path-to-hermes-source>"
export HERMES_TEST_PYTHON="<absolute-path-to-hermes-python>"
export TMPDIR="<absolute-path-to-private-scratch>"
export TMP="$TMPDIR" TEMP="$TMPDIR" PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=''
export HERMES_REQUIRE_HOST_TESTS=1
"$HERMES_TEST_PYTHON" -m unittest discover -s tests -v
```

The interpreter must have the test and host dependencies already provisioned. The dedicated host integration job must run on Windows with `HERMES_REQUIRE_HOST_TESTS=1`; missing or invalid prerequisites fail rather than skip. Without that flag, host tests skip with an explicit reason when prerequisites are unavailable. Host child processes use isolated scratch homes; approvals in these tests are simulated callbacks, not human approvals. Offline tests exercise synthetic fixed MCP calls, a loopback REST handler, and a local Git clone; they do not exercise live GitHub cloning or third-party MCP servers.
